# Trace storage: JSONL vs SQLite

- Generated by `experiments/trace_storage/run_benchmark.py` on Windows 11, Python 3.13.5.
- Payload: synthetic API-line trajectories at 1,000 / 5,000 / 20,000 / 50,000 records, 4 tool steps / ~1.6 KB each.
- Timings are the median of 2 runs; `lookup` resolves the *last* task id, i.e. the JSONL worst case.

| 记录数 | JSONL 写入 | JSONL 全量读 | JSONL 单任务查 | JSONL 失败过滤 | SQLite 写入 | SQLite 全量读 | SQLite 单任务查 | SQLite 失败过滤 | 磁盘 (JSONL / DB) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 60.20 ms | 87.81 ms | 35.52 ms | 4.57 ms | 169.92 ms | 56.56 ms | 2.37 ms | 1.83 ms | 2.3 MB / 4.2 MB |
| 5,000 | 279.64 ms | 397.65 ms | 171.24 ms | 14.36 ms | 808.60 ms | 412.52 ms | 1.95 ms | 1.93 ms | 11.6 MB / 20.7 MB |
| 20,000 | 1110.44 ms | 1838.80 ms | 675.38 ms | 50.41 ms | 3173.63 ms | 1919.27 ms | 1.89 ms | 2.39 ms | 46.5 MB / 82.8 MB |
| 50,000 | 2948.14 ms | 5149.34 ms | 1677.52 ms | 126.03 ms | 7952.72 ms | 4590.76 ms | 2.19 ms | 2.99 ms | 116.2 MB / 207.2 MB |

## 结论

1. JSONL 的单任务查询与全量读都是 O(N)：记录数从 1,000 增至 50,000（50×）时，最坏查询从 35.52 ms 变为 1677.52 ms（47.2×），因为必须逐行解析直到命中。
2. SQLite 走主键/二级索引，查询耗时基本不随 N 增长：2.37 ms（1,000 条）→ 2.19 ms（50,000 条）。全量读仍是 O(N)，但只解析 payload 列：5149.34 ms → 4590.76 ms。
3. 写入反过来：JSONL 一次顺序写更快（2948.14 ms vs 7952.72 ms，50,000 条），磁盘占用也更小（116.2 MB vs 207.2 MB）。写只发生在每轮结束一次，读却会被报告页反复触发，因此规模上来后 SQLite 划算。

**失效阈值**：单 run 轨迹数 ≤ 1,000 条（约 2.3 MB）时，JSONL 全量读 87.81 ms、单任务查 35.52 ms，交互无感；到 5,000 条时全量读 397.65 ms，开始可感知；50,000 条时分别达到 5149.34 ms / 1677.52 ms，报告页每次刷新都是秒级。**单 run 超过约 5,000 条轨迹就应切到 SQLite**（索引查询恒在 2 ms 量级）；≤ 1,000 条继续用 JSONL 最省事。当前示例 run 为 12 条任务 × 4 轮 = 48 条，远低于阈值，故默认仍是 JSONL。

## 落地方式

```yaml
store:
  backend: sqlite      # 默认 jsonl
  sqlite_name: traces.db
```

两种后端实现同一个 `TraceStore` 协议（`harnessloop/store/trace_store.py`），`LoopRunner` 只依赖协议，因此报告与 UI 无需改动，JSONL 仍是默认值（可 diff、无需额外工具）。

## 复现

```bash
python experiments/trace_storage/run_benchmark.py
```
